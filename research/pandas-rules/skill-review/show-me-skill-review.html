Why a result from assign can be trusted

Your sense that the data stays inside the frame matches what I measured. A column read through the lambda or through pd.col comes from the frame itself, so its rows always line up. The one way I found to get a frame back with missing data and no error is to pass a column from another frame: source.assign(residual=source["load"] - other["solar"]) returned [nan, 15.0, 24.0] when the two indexes differed. An array of the wrong length raised.

The pandas 3.1 methods and type checkers

pandas-stubs 3.1.0 does not know DataFrame.select or filter(cond=). mypy and pyright both report correct calls to them as errors. Three rules in the proposal rewrite code to those two methods, and step 5 recommends pandas-stubs, so a project that follows both would get type errors on correct code.

What the measurements support. Neither form is faster or safer overall. The lambda works everywhere, and pd.col gives a better error for a misspelled column and is shorter. A rule that rewrites one to the other moves code between two equal forms, and it leaves a mixed style, because np.where and calculations across columns still need the lambda.

An alternative that keeps what you like

output_columns = ["residual_load", "net_export"]
features = source_data.assign(
    residual_load=pd.col("load") - pd.col("wind") - pd.col("solar"),
    net_export=pd.col("outgoing") - pd.col("incoming"),
)[output_columns]

It keeps assign and the named list. It gains the better error message and drops the repeated lambda df: df[...]. It loses the single style, because some columns will still need a lambda.

A named list of columns

A named list costs nothing, and the way you apply it is the safe one. With one name missing from the frame, frame[output_columns] and frame.select(output_columns) both raised KeyError: "['y'] not in index". frame.filter(items=output_columns) returned the frame without the missing column and without an error.

What the measurements support. Keep the shape. pdx can also enforce it with a new rule that reports a list of several column names written inside a call or a subscript. The proposal has no such rule today, and the number of names that triggers it is your call.

Above that, s.map(lambda v: mapping.get(v, v)) keeps the same meaning at a flat cost of about 85 ms. The category form is the fastest one with the same result, at about 58 ms for text and 5 ms for integers, and it only works when no two keys end at the same value. The proposal page recommended map(mapping).fillna(s), which was wrong in the two cases above, and I have corrected the page.

Decisions for you

  1. lambda-column. It rewrites your lambdas to pd.col, and the second PR of the build adds it with a safe fix. I recommend turning it into a rule that only reports, or removing it. Removing it fits the measurements best, because the two forms are equal.
  2. assign-then-select. It rewrites frame[cols].assign(...) to select. I recommend removing it, because the shape it replaces is as fast and type checkers do not know select yet.
  3. query-string and filter-items. I recommend keeping both and changing their targets to forms that type checkers accept. query strings would point to .loc[pd.col(...) > 1], and filter(items=cols) would point to frame[cols], which also raises on a missing name.
  4. A rule for inline column lists. Say whether you want it, and from how many names.

Method: pandas 3.1.1, Python 3.15.2 and pyarrow 26.0.1 on a machine with 32 cores, while the build agent was also running, so small differences are noise. A time is the best of 3 to 7 runs on a frame held in memory. The scripts and raw output are in research/pandas-rules/skill-review.
